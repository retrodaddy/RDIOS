## What this milestone was

The founder's own framing: a founder should be able to search the institution itself, not one application at a time. Search is institutional memory, not navigation — everything searchable already exists somewhere else, and Search only discovers it, never owns it. The closing test, asked constantly while building: if Tamizhi (M13, not built here) were built tomorrow, would this Search layer already give it everything it needs to discover institutional knowledge without knowing where that knowledge lives? Every design decision below was built to answer yes to that question, then stopped there — no more was built once the answer was already yes.

## Core design — Search queries the platform, never a domain directly

`engines/search/` is the second Shared Engine Layer piece after Authority (`engines/authority/`), following the identical discipline: a small, generic engine every application composes with, never a parallel description of any application's own data.

- **`engines/search/types.ts`** — `SearchResult` carries exactly the brief's own seven fields (Icon, Title, Type, Description, Status, Last Updated, and `href` as the one Primary Action). Nothing more — no per-result action menu, no embedded mutation capability. `SearchApplication` is the brief's own closed ten-item scope (People, Organization, Work, Finance, Assets, Community, Projects, Documents, Reports, History) — `finance` and `assets` kept as two distinct application values even though both read from `applications/finance`, because the brief itself named them as two separate scope entries.
- **`engines/search/index.ts`** — one adapter function per application (`indexPeople`, `indexOrganization`, `indexWork`, `indexFinance`/`indexAssets`, `indexCommunity`, `indexProjects`, `indexDocuments`, `indexReports`, `indexHistory`), each reading the exact same mock provider every application's own page already reads. `searchInstitution()` is the one composed entry point — institution-scoped, query-required (an empty query returns nothing rather than dumping the whole institution).
- **`engines/search/rank.ts`** — deliberately simple, per the brief: exact title match, title-starts-with, title-contains, keyword match, description match, then recency as a tiebreaker within a tier. Five explainable numeric tiers, nothing AI-driven, nothing semantic, nothing vector-based. A founder (or Tamizhi, later) can always explain why one result outranked another.
- **`engines/search/actions.ts`** — the one client-callable entry point, `searchAction`. Institution scoping comes entirely from the caller's own resolved session (`getIdentityContext()`), never a client-supplied institution id — the same "governance is automatic, not bolted on" shape every other action on this platform already uses, and the entire answer to "no permission bypass, no hidden metadata leaks": cross-tenant leakage is structurally impossible, not merely checked.

## Search-readiness audit — no schema changes needed

The brief's own instruction was to verify every domain exposes sufficient metadata and extend only where genuinely missing, never redesign a domain to get there. The audit found one real gap: most domains (Position, Contact, WorkItem, FinanceTransaction, Asset, Project) have no explicit `modifiedAt` field the way Document already does. Rather than touching six already-frozen milestones' schemas and every mutating action within them — which the brief explicitly ruled out — "Last Updated" is derived honestly at read-time in each adapter: the latest of whichever real timestamps that record already has (`createdAt`, `completedAt`, `decidedAt`, `archivedAt`, a Contact's relationships' `lastActivityAt`). Zero fields were added to zero prior domains. This is named directly in the Technical Debt Register as a real, if minor, inconsistency (two records "really" touched at the same instant could show different precision depending on which application they came from) rather than smoothed over.

## Opening a result never duplicates a screen

This was the hardest part of the brief to honor literally: "selecting a result should open the existing experience... never duplicate screens." A universal search result needs to open six different applications' own detail drawers, each of which lives inside a Client Component that manages its own `selectedId` state internally.

The solution: every result's `href` is a deep link into the owning application's own existing page (`/work?open=<id>`, `/money?open=<id>&tab=assets`, `/customers?open=<id>`, `/projects?open=<id>`, `/documents?open=<id>`, `/reports?open=<id>`, `/people/organization?open=<id>`, or a Person's own existing profile page directly, which needs no query param since it's already a dedicated route). Each of the seven board components (`WorkBoard`, `MoneyBoard`, `CommunityBoard`, `ProjectBoard`, `DocumentsBoard`, `ReportsBoard`, `OrganizationCanvas`) gained one small, additive prop — `initialSelectedId` (and `MoneyBoard` an `initialTab`) — read from the page's own `searchParams` and used to open that exact drawer pre-selected. No new detail view, no new visual language, was built anywhere; this is purely additive wiring into markup that already existed.

**A real bug was found live, not invented to justify the sprint.** React only honors a `useState` initializer on a component's first mount. Since a Search-driven navigation is a client-side `router.push` on an already-mounted page, opening a *second* search result without a full page reload left the drawer showing the previous selection, or nothing — the prop changed, but the state that reads it once at mount time never did. Confirmed live: searching for a Task and opening it worked as expected on first mount, but the identical action for a second result (a Document, navigated to cross-page from Home) initially failed to open the drawer at all, only the list. Fixed by adding one `useEffect` per board — `useEffect(() => { if (initialSelectedId) setSelectedId(initialSelectedId); }, [initialSelectedId])` — syncing the selection whenever Search hands the page a new id. Re-verified live afterward: both a same-page (Work → Search → open the same page's own Task) and a cross-page (Home → Search → open a Document) navigation correctly opened the real, existing drawer with its full Timeline intact.

## Governance, History, Attention — exactly as instructed

- **Governance**: reused, not reinvented. No new permission model — Search reads exactly what every existing page already reads, gated only by the same institution scoping every provider call already has. Per-record visibility stays exactly as open as it already was (every prior Be Aware rollup already showed institution-wide aggregate facts to everyone; Search doesn't change that policy, it only makes the same already-visible facts findable by name).
- **History**: nothing. No search is ever narrated — `searchAction` never calls `recordHistory`. Opening a result continues that record's own existing Timeline unchanged, exactly as the brief specified.
- **Attention**: nothing. Search contributes zero Act Now items, zero Be Aware lines. Attention is proactive, Search is reactive, and the two engines share no code path in either direction.
- **Filters**: Application, Status, and Date are real and composable with the query in the overlay UI. Type is real in the engine (`SearchFilters.type`, `applyFilters`) but deliberately not exposed as a UI control this pass — with ten applications each naming wildly different `type` values, a single dropdown felt like exactly the kind of complexity the brief's "no BI platform" instruction warned against. Named honestly in the Technical Debt Register as a real seam, not yet a real control.

## Honest assessment — where this fell short of the full ask

- **Multi-user walkthrough was not performed.** Only one real person (the founder) was available in the test institution. Governance was verified by code review (institution scoping is structural, not a per-query check that could be forgotten) rather than by a second person's live session confirming they see the same institution-scoped results and nothing from another tenant.
- **Cross-institution isolation was verified by code review, not by two live institutions searched side by side.** `searchAction` resolves `ctx.institution.id` from the caller's own session and every adapter takes that as its only scope parameter — there is no code path by which a query could read another institution's data — but this session didn't stand up a second institution to prove it empirically the way M7/M8's cross-institution passes did.
- **Only two of the ten searchable applications (Work, History) were exercised in the live walkthrough's actual search results**, plus Documents via the deep-link test. The other seven adapters (People, Organization, Money, Assets, Community, Projects, Reports) were verified by code review against their real provider shapes, not by creating a record in each and confirming it appears in a live search result.
- **The Type filter is real in the engine but not exposed in the UI**, and Search's ranking doesn't yet account for whether the searching person actually holds the Area that would let them act on a result — both named directly in the Technical Debt Register as deliberate, bounded simplifications rather than gaps discovered after the fact.

None of the above blocks anything. ARUMBU now has one real, honest discovery layer sitting above every domain built through M11 — reusing every existing drawer, every existing permission boundary, every existing Timeline, inventing nothing new to show a founder what the institution already knows. Per the founder's own roadmap: this was the necessary step before Tamizhi (M13) can reason across a complete platform instead of querying eight applications individually.
